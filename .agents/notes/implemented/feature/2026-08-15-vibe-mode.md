# Agent Note: Vibe mode with the fixed agent-cluster workflow

Status: implemented

English | [中文](2026-08-15-vibe-mode.zh.md)

## Problem

The mode system shipped advisory modes plus one enforced mode (design), but the requested vibe mode is a process, not a behavior: a fixed agent cluster — product manager, architect, UI designer, frontend/backend engineers (multiple instances per module), and a test engineer — with issue escalation back up the chain and user-decision points at the product/architecture/UI layers.

## Decision

`vibe` joins the `AgentMode` union, and a new tool package, `@deepseek-ai/dsh-tool-vibe-workflow`, ships the cluster as a canned workflow over the existing `ctx.workflowEngine` seam — the same engine the `workflow` tool uses, so parsing, execution, caps, cancellation, and child spawning stay behind the established boundary.

The `vibe` tool takes `request` (plus optional `answers` from a previous run) and runs one canned script: the product manager clarifies and archives requirements (asking the user directly when it can, otherwise returning open questions); the UI designer and the architect run in parallel; the architect's modules spawn one frontend and/or backend engineer per module (multi-instance fan-out), each implementing in small parts with per-part unit tests; the test engineer reviews the whole delivery; reported issues escalate to the architect, who assigns fixes, engineers apply them, and the test engineer verifies.

User decisions route through the calling agent by design: children may or may not have the `ask_user` tool, so the script returns `needs-input` with the open questions and the main agent asks and re-runs with answers — the "产品/架构/UI 可直接询问用户决策" requirement holds through whichever path is available. The vibe-mode guidance section tells the agent to run the `vibe` tool and to loop on needs-input.

## Alternatives considered

- **Guidance-only vibe** — the mode text alone says "orchestrate the cluster yourself with the workflow tool". Rejected: a fixed cluster needs a fixed script; hand-written orchestration would drift per call and lose the structured role/phase contract.
- **A new engine** — a dedicated cluster executor beside `workflowEngine`. Rejected: the engine seam already provides scripts, phases, caps, cancellation, and child spawning; the tool adds only the canned script and its schema.
- **Cluster state in the mode package** — agent-modes owns the workflow. Rejected: tool surface belongs next to the other workflow tools (`tool-workflow`, `tool-ralph`); agent-modes stays the mode vocabulary and enforcement, and the mode guidance references the tool.

## Consequences

- Vibe mode has one deterministic process: one tool call runs the whole cluster, and needs-input runs resume with answers instead of restarting.
- The cluster is bounded: one escalation round, engine caps on concurrency and total agents, and the parent turn blocks until the run settles.
- The Web surface gains one tool row and the `/mode` popup one entry; the base bundle mounts the tool so every surface that has `workflowEngine` can use it.
- The canned script is a package constant pinned by tests (syntax, phases, roles, no template-literal hazards); the tool's engine handoff, stop-reason mapping, and no-agent guard are unit-tested against a stub engine.
