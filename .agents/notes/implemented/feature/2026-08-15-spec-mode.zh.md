# Agent Note：用户主导设计 + 一气呵成集群执行的 Spec 模式

Status: implemented

[English](2026-08-15-spec-mode.md) | 中文

## Problem

vibe 集群拥有执行流程但不拥有设计：产品经理猜测、架构师决定，适合"直接开工"的请求。要求的 spec 模式把前半段反转——由用户主导把设计讨论细化到模块级——之后仍须一次跑完全部交付，且不再重跑用户已敲定的澄清阶段。

## Decision

`spec` 加入 `AgentMode` 联合，`vibe` 工具的 canned 脚本新增三个 spec 模式预填：`requirements`（已确认的需求档案）、`design`（已确认的模块级技术设计）与 `styleGuide`（已确认的样式规范）。每个预填跳过对应的集群阶段——产品经理、架构师或 UI 设计师——而工程师、测试工程师与升级循环始终运行。预填设计缺少模块形态（`modules` 含 `id`/`title`/`layer`/`tasks`/`acceptance`）时脚本大声失败。

spec 模式指引段落驱动交互式前半段：agent 就目标、约束、技术偏好与模块拆分询问用户，直到用户确认模块级设计，然后带已确认的需求与设计预填一次运行 `vibe` 工具——"确认后全量并行执行 vibe 流程一气呵成"。

## Alternatives considered

- **独立 spec 工具** —— 在 `vibe` 之外建专用工具。拒绝：集群脚本相同；预填只是更早敲定的阶段，一个带可选预填的工具让执行路径保持单一。
- **只写进模式提示词** —— spec 指引说"先讨论，再调 vibe"；集群会带着讨论文本重跑 PM/架构师。拒绝：重复澄清浪费 agent，且可能偏离用户已确认的内容；预填让用户决策成为权威输入。
- **预填校验** —— 按架构师 schema 复验预填设计。拒绝（对当前形态）：设计来自用户确认的讨论，因此只大声检查脚本依赖的形态（`modules` 数组）。

## Consequences

- Spec 模式只有一条确定性弧线：用户主导讨论到模块级，然后一次 `vibe` 调用带已确认产物一气呵成执行集群。
- vibe 脚本与 schema 新增三个可选参数；弹出层与模式词汇新增第五种模式。
- 预填误用在模块形态检查处大声失败，而不是静默错执行。
